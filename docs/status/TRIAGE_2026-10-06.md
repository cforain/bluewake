## History-intro audio (#97, related #65)

The [Windows reporter's log](https://github.com/chrissotraidis/bluewake/issues/97#issuecomment-5996307585)
records this sequence with mods mask 0x0:

| Retrace | Track | Sound state |
| --- | --- | --- |
| 1977 | prior filename still title.afc | 2 (preparing) |
| 1979 | 1tale.afc | 3 (ready) |
| 2081 | 1tale.afc | 4 (playing) |
| 2083 | 1tale.afc | 0 (idle) |

The last two lines are 25 ms apart by the Windows timestamps. Retraces are guest time, so the triage
script reports two retraces rather than converting them into wall time. The earlier `sea_T` demo
summary occurs before name entry and does not describe this history intro. General mixed sound can
also be ambience without the expected music. Previous tests that accepted state 4 or `missing=0`
therefore did not settle the report.

Narrow source review of [JAIStreamMgr.cpp](https://github.com/zeldaret/tww/blob/a1854d47ce5aa9d0f21c7fb5a71aaade63659693/src/JSystem/JAudio/JAIStreamMgr.cpp)
shows that the stream manager can clear an active sound when `StreamLib::getPlayingFlag()` returns 2,
or during release/fade handling. This supplies competing paths to trace, not proof of which ran.
The affected Windows log records all five native accelerator groups on; the Mac comparison records
them off. This is a real comparison difference, not proof of a cause. The native math entry set is
SDK matrix math, so it should not be casually equated with a replacement audio decoder.
The flags and counters are identified by GZLE01 revision-0 symbols; the existing host observes the
same JAIZelBasic stream slot. Some functions in this reference are nonmatching/incomplete, so generated
code and actual runtime evidence remain authoritative for a fix.

### Title-to-intro reproduction and callback ordering

A subsequent bounded run on the same Apple Silicon Mac reproduces the Windows failure. The previous
immediate-entry test skipped the title track and therefore missed this transition. An opt-in
`BLUEWAKE_PAD_TITLE_DELAY=900` extends the existing title-ready route; the confirmation pulse waits
until the delayed primary pulse has finished. The unset/default route is unchanged. Accepted values
are 0..3600 retraces and require `BLUEWAKE_PAD_PULSE_ON_TITLE_READY=1` to have an effect.

With fresh scratch card/settings/SRAM, Metal/HLE, no mods and Smooth Motion off:

- Title ready at 333; primary pulse at 1234; confirmation at 1237; intro scene at 1692.
- `1tale.afc` ready at 1785, playing at 1887, idle at 1889. The new fields retain `stop=1/0`,
  `play=0/2`, `dvd_pending=1`, `starting=1`, with the title track's sample counts unchanged.
- The 3600-retrace run exits normally. Its captured final ten seconds have zero nonzero samples.
- The same host's default immediate-entry control reaches playing at 1001 and stays there through
  exit at 2600. Its final ten seconds contain 639128 nonzero samples, peak 13600. This is captured
  mixer-output evidence, not a physical-speaker listening test or proof of every cutscene cue.

The ordering is visible in source and a new four-line-capped `[music-dvd]` trace:

1. The host intercepts DVDReadAsyncPrio at 0x8030FADC and runs the completion callback inline before
   returning to the caller at 0x8029D2E8.
2. The stream callback at 0x8029D1C8 clears DvdLoadFlag. The first observed completion reports pending
   0 before and 0 after, completed=1; later calls report 1 before and 0 after.
3. The local generated caller sets DvdLoadFlag to 1 at 0x8029D2EC, after returning from the intercepted
   read. Consequently the completed read is left marked pending. No generated code is committed.
4. When switching tracks, the stream callback at 0x8029D7C0 waits for this flag to clear before calling
   `__start`. It retains the title track's finished playflag2=2. The stream manager then discards the
   new sound on its next playing-state update, accounting for the two-retrace lifetime.

This reproduces the sequence without Windows, D3D12, HD textures or native accelerators. It explains
the history-intro failure; other missing scripted cues in #65 still need their own validation.
The next fix should model asynchronous completion after the caller resumes, preserving callback
register/scheduler rules and pending work across save-state loads. Do not clear the music flag by
address as a workaround or alter all DVD timing without a focused regression check. No callback
timing behavior is changed in this diagnostic PR.

Validation: Mac host builds; the existing PAD event-schedule and audio-watch tests pass. Negative,
out-of-range and nonnumeric title delays reject before guest execution. The two complete routes above
use separate scratch data. Windows CI is the compile gate, with Windows hardware still untested.

## Flickering regression (#136)

The original 0.4.0 source tag resolves to `d102695a` in Wind-Waker-Recomp. Its builder profile declares
RecompCore `8ab24da`; BlueWake 0.5.0 pins `95a6a47`. This identifies source candidates, not independently
verified provenance of every historical binary. `git log` over that runtime range includes:

- `7ae7d03189`: reuse consecutive draw transform constants.
- `8e44621677` / patch 0153: indexed mesh positions/UVs and screen-space matching.
- `0b86924175` / patch 0155: restrict vertex blending to positions written by the game.
- `ea30f6fbaf`: interpolate pixel colours; `6fd14f6698`: cloth strip blending.
- `14a1cea84c` / patch 0154: sample an HD replacement's own mip levels.
- `7e5c7d4fd9`, `6c853a1d90`: ubershader fallback while specialized pipelines compile, default on D3D12.

First isolate original 30 FPS vs Smooth Motion 60/120 in the same scene, with original textures.
A clean base frame but bad intermediate frames points toward matching/UV/pixel interpolation; a
base-frame problem needs a different path. The new UV interpolation includes a half-texture jump
check, so merely noticing wraparound is not a diagnosis. Cold-only D3D12 flicker would elevate the
fallback shader candidate; steady warmed-cache flicker would weaken it. HD mip sampling only applies
to replacement textures and cannot explain a pack-free failure by itself.

A bounded Mac/Metal title-view capture at Smooth Motion 60, no texture pack, produced seven real/
in-between frame pairs. Inspection of one pair and its adjacent real frame did not isolate the
reported disappearing clouds/waves; it is not the reporter's exact scene. A 30 FPS control run
completed but the interpolation dump is inactive with Smooth Motion off, so it did not produce
matching comparison frames. Do not treat that run as a matched image comparison.

No report capture or NVIDIA reproduction yet. Do not revert several rendering changes at once or
claim the dungeon-map repair will fix this: patch 0157 is newer than 0.5.0.

## Controller dead zone (#138)

The input chain is more specific than a generic XInput hypothesis:

- Aurora's `input.hpp` enables the default per-axis cutoff of 8000. Its `pad/pad.cpp` converts
  values strictly above that cutoff by dividing by 256, without subtracting/rescaling the dead zone.
- `GXRuntime/backends/aurora/aurora_input.cpp` copies PADRead stick values directly. It does not call
  Aurora's separate PADClamp implementation. BlueWake's `pad_wire.c` offsets signed stick values by
  128 for the guest SI representation; it does not rescale them.
- The local GZLE01 generated game code calls guest PADClamp at 0x80314C90 from 0x802C39AC. Its
  ClampStick at 0x80314B60 subtracts the dead zone before clipping to the stick envelope. Inspection
  of ClampRegion at 0x80370FA8 in Chris's local disc-derived DOL verifies main-stick min 15, max 72
  and diagonal 40. No generated code or disc bytes are committed with this record.
- For a positive horizontal movement with Y=0, SDL value 8000 produces zero; 8001 produces host 31,
  then guest 16. That is 22.2% of the guest maximum 72, consistent with the reporter's jump.
  The axial maximum starts at host value 87 (15+72), about 68% of SDL travel, rather than the
  reporter's estimated 56%. This is a source/data calculation, not a physical-stick measurement.

This identifies a concrete discontinuity and confirms stacked clamping for the local supported disc.
It does not validate a replacement curve on the reporter's controller. Simply removing the host
cutoff retains the early saturation; rescaling without considering the guest clamp can add excessive
dead travel. The candidate should account for both layers, preserve full travel and check slow aiming,
diagonal movement, center drift and the right stick on hardware. No input behavior was changed here.
